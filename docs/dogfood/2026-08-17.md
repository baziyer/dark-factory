# Dogfood log — 2026-08-17, first floor (v0.1.0)

The first end-to-end run of the released binary on the owner's machine:
`factoryctl init` from the v0.1.0 tarball (Codex dogfood account via
`CODEX_HOME=~/.codex-dogfood`), one backlog item handed to the orchestrator
(`god`, Codex), which created a worker (`first-floor-worker`, Codex),
composed and assigned a task, and monitored it while the worker made the
change, ran the gate and opened a PR. Everything below was observed live;
each `###` entry is one issue in the format `scripts/import-issues.sh`
turns into a labelled GitHub issue (GitHub's API was returning 503 during
the run, so they were captured here first). Fixes reference the entry title
until the issue number exists.

What worked: install/migrate to `~/.dark-factory/bin/current` with the
launchd job rewritten and `CODEX_HOME` carried; `factoryctl update` sees the
release; `task assign` spawns the orchestrator's session instantly; the
orchestrator drives `factoryctl` from its own session (agent add, task add,
task assign, session list, task get); the worker finds and fixes the right
line, runs the gate; hooks other than `SessionStart` fire and drive session
state; the TUI shows the two sessions side by side and the WORKSHOP task
tree.

## Sessions and hooks

### Codex 0.147: SessionStart never fires at TUI startup, so every Codex session stays `starting` until nudged by hand

**Symptom**: both real Codex sessions of the run (`god`,
`5a461489…`; `first-floor-worker`, `786f6950…`) rendered their prompt within
seconds and sat in `starting` indefinitely (2 min and 1 min observed) with no
task delivered. Posting the session's own hook by hand — `printf '{}' |
factoryctl hook --token-file $DARK_FACTORY_HOME/runs/<session>/hook.token
SessionStart` — moved each to `idle` at once and delivery followed; every
later hook (UserPromptSubmit/PreToolUse/PostToolUse) then fired normally.
This is #24, but it is deterministic, not intermittent: 2 of 2 sessions
tonight, and the same in a throwaway `CODEX_HOME` with only a SessionStart
hook (25 s at the prompt, nothing fired).
**Evidence**: generated `agents/god/codex-home/config.toml` has the
`[[hooks.SessionStart]]` block with `type = "command"` and the factoryctl
command; `codex features list` reports `hooks stable true` for that home;
Codex printed `clamping SessionEnd hook timeout to 3s` (so it parsed the
hooks table) and its binary lists SessionStart sources
`startup/resume/clear/compact`. `--dangerously-bypass-hook-trust` is passed.
**Suggested fix**: root-cause in Codex's `hooks/src/events/session_start.rs`
for the exact 0.147.0 build (does startup fire before the hooks table is
loaded, only on `resume`, or only when a thread is created lazily?), then
either configure what Codex needs or add a daemon-side startup handshake
that does not read terminal output. Until then the manual nudge is the
operator escape hatch and #52's deadline+backoff would loop on it — the
deadline PR must not land as the only answer.
**Size**: M.

### Codex sessions block on approval prompts for every `factoryctl` call and for `git push`, so an unattended factory stalls

**Symptom**: `god`'s first `factoryctl agent add …` stopped on Codex's
"Would you like to run the following command?" prompt; its own explanation:
"The initial worker creation was blocked by the sandbox's local-socket
restriction, so I requested the required factoryctl access." Every later
`factoryctl` call and even `sleep 30; factoryctl task get …` prompted again
until the operator chose "don't ask again for commands that start with
`factoryctl`". The worker will hit the same at `git push`/`gh pr create`
(no network in the sandbox).
**Evidence**: `crates/factoryd/src/providers/codex.rs` writes
`sandbox_mode = "workspace-write"` and `[sandbox_workspace_write]
network_access = false`, and passes `approval_policy` only when the agent
profile sets a permission mode (`god`'s profile is empty → Codex default
`on-request`). Seatbelt's `network_access = false` also denies connecting to
the daemon's unix socket.
**Suggested fix**: decide the unattended policy per role and make the
generated Codex home carry it: pre-seed the same prefix approval Codex
writes for "don't ask again for `factoryctl`" (find where 0.147 persists it
— rules file or config key — and write it in the dark-factory config
block), give worker sessions network access (they must push) or route
push/PR through the daemon, and set `approval_policy` explicitly instead of
inheriting Codex's default. Document the resulting boundary in
docs/providers.md.
**Size**: M.

### A session blocked on a provider approval prompt still shows `working`

**Symptom**: while `god` and the worker each sat on a Codex approval prompt
for minutes, WORKSHOP showed both `working`, FORTRESS gave no signal, and
`g`/`G` had nothing to jump to. The operator only found out by reading the
terminal.
**Evidence**: the daemon subscribes to SessionStart, UserPromptSubmit,
PreToolUse, PostToolUse, Notification, Stop, SubagentStop, SessionEnd
(`ProviderHookEvent` in `crates/factory-core/src/lib.rs`); Codex 0.147 has
a `PermissionRequest` hook event (`permission_request` in the binary next
to the others) that is not configured, so the state source has no way to
know.
**Suggested fix**: add `PermissionRequest` to the hook events the Codex
provider writes and the daemon accepts; map it to
`SessionState::WaitingForInput` (already `Attention::NeedsInput`, so
`factoryctl status`, `g`/`G`, FORTRESS glyphs and announcements light up
with no further code); the next PreToolUse/PostToolUse returns the session
to `working`. Check what Claude Code's equivalent is (its `Notification`
hook with a permission matcher) so both providers report the same state.
**Size**: M.

## TUI

### Zooming in from a selected worker lands on the orchestrator's terminal

**Symptom**: on WORKSHOP's agents pane with `first-floor-worker` selected,
Enter opened TERMINALS with `god`'s pane focused (highlighted border,
receiving keys). Same from FORTRESS with the cursor on the worker's glyph.
**Evidence**: `crates/factory-tui/src/model/keymap.rs` `zoom_in_workshop`
(Agents arm) sets `selected_agent` and switches to `View::Terminals`, but
TERMINALS' focused pane / key target is not derived from `selected_agent`
(see `ui/terminals.rs` and the pane-forwarding target in `main.rs`).
**Suggested fix**: one source of truth — the focused TERMINALS pane is the
pane of `selected_agent` (falling back to the first tile only when the
selected agent has no live pane), used for both the highlight and the key
target; a model test that zooms from the second agent and asserts the
focused pane.
**Size**: S.

### TERMINALS forwards every key to a pane by default, so Tab/j/k/1-4 look dead and there is no visible mode

**Symptom**: entering TERMINALS (by `3` or by zooming) silently turns
pane-forwarding on: `1`–`4`, Tab, `j`/`k`, `q` all go into the focused
terminal (the operator's `1`/`2` presses ended up typed into `god`'s Codex
composer as `2111121p`), including when there are **no** live panes at all
("no live sessions" screen). Only the status-bar hint `Ctrl-] board control`
explains it. Moving between terminals therefore needs Ctrl-] first, which
reads as "navigation is broken".
**Evidence**: `keymap.rs` `switch_view`/`zoom_in` set
`pane_forwarding = true` for Terminals and Focus; `handle_normal_key`
returns `Intent::ForwardKey` before consulting the keymap.
**Suggested fix**: TERMINALS defaults to board control (Tab/j/k/arrows move
focus between panes, Enter zooms into FOCUS, `i` or Ctrl-] starts typing
into the focused pane); FOCUS defaults to typing (you zoomed in to talk to
it) with Ctrl-] returning to board keys; never forward when no pane exists;
the status bar states the mode in words (`TYPING → god  Ctrl-] board` vs
`BOARD  i type`). Model tests for each.
**Size**: S–M.

### Announcements repeat identical session states dozens of times

**Symptom**: 65 announcements in a few minutes, almost all `god session
working` / `first-flo… session working` — every hook that touched the row
announced the same state again, drowning the four real transitions.
**Evidence**: `crates/factory-tui/src/model/announcements.rs` formats each
`session_changed` event; the daemon emits one per hook, state unchanged.
**Suggested fix**: announce a session only when `state` (or attention)
actually changed since the last announced snapshot for that session;
`activity`/last-hook updates stay in the detail pane.
**Size**: S.

### Key hints disappear for a while after cancelling a prompt

**Symptom**: after Esc out of the message/new-task prompt the status bar's
action hints are gone for several seconds, so the operator does not know
what keys work.
**Evidence**: the status bar shows the transient status message
(`set_status`) instead of the hint line until it expires.
**Suggested fix**: render the hint line always and show the transient
status beside it (or above it), never instead of it.
**Size**: S.

### A freshly opened board has no history: announcements start empty

**Symptom**: `factory-tui` opened after an hour of activity shows
`announcements (0) — (nothing yet)`; announcements exist only inside the

**Size**: S.

### Decision (taken 17 Aug, evening): two screens — BUILDING and AGENT — replace the four views

**Symptom**: the owner's read after the first run: FORTRESS with one
project and two glyphs has nowhere to move and no obvious purpose; WORKSHOP
duplicates the same list; TERMINALS side-by-side panes with no context is
confusing; `1`–`4` view switching plus a hidden forwarding mode is more
state than the job needs.
**Evidence**: screenshots from the run; `?` help exists but is
undiscoverable; README has no per-view guide.
**Decision**: the TUI becomes two screens and two modes (BOARD / TYPING).
*BUILDING* (home): a visual cross-section, one floor per agent (glyph,
name, provider, state colour, activity sparkline from hook events, queue
depth, current task, ═ routes), floors grouped by project; beside it
*NEEDS YOU* — the attention list `factory-core::attention` already
computes (waiting for input, failed, blocked, questions), oldest first,
`g` selects the next; `j`/`k` move between floors, Enter opens the agent;
`n` new task, `m` message, `o` message the orchestrator, `x` stop, `p`
project. *AGENT*: the agent's live terminal large; its queue (assigned +
running tasks) and inbox alongside; a settings panel (model, permission
mode / approval policy, instructions.md, memory.md, pause) whose edits go
through the existing `factoryctl agent profile set` / pause / resume
requests (instructions/memory open in `$EDITOR` with the TUI suspended);
`[`/`]` (or `j`/`k` in board mode) switch to the previous/next agent
without leaving the screen; `i`/Enter type into the terminal, Ctrl-] back
to board keys, `z` maximises the terminal, Esc back to BUILDING. The
orchestrator's AGENT screen additionally shows the project-wide queue
(unassigned + per-worker) and the delegation graph. Deleted: FORTRESS/
WORKSHOP/TERMINALS/FOCUS as separate views, `1`–`4`, side-by-side
terminals. Sequence: land the navigation fixes first (they carry over),
then this rewrite as one PR that leaves keymap.rs smaller, then the README
section per screen.
**Size**: L (decision taken; implementation pending).

## Orchestration

### Orchestrator restarts and replaces a worker it cannot see is blocked, cascading with the two Codex problems above

**Symptom**: `god` stopped `first-floor-worker`'s session at 18:17 (the
worker was sitting on the `git push` approval prompt with its edit
uncommitted), the respawn stalled in `starting`, `god` created
`first-floor-worker-2` and reassigned the task (18:20), that session
stalled too, `god` paused the original worker (18:21). Net: three stopped
sessions, one paused agent, one duplicate agent, the finished edit stranded
in the first worktree, no PR.
**Evidence**: `events` table 18:17:10–18:21:32 (session_changed stopped →
starting × 3, agent_changed paused:true, agent first-floor-worker-2
created); god's guidance lists `factoryctl session stop` and it followed
"monitor the worker" literally.
**Suggested fix**: mostly falls out of the entries above (a visible
`waiting_for_input` state; sessions that reach `idle` on their own; no
approval prompts for factoryctl/push). Beyond that: orchestrator guidance
should say what to do when a worker is waiting for input (route it to the
operator via `factoryctl agent message`/attention, don't stop it), and a
worker's uncommitted work should never be silently orphaned when its
session is stopped (at least surface "worktree dirty" in agent status —
`factoryctl agent status` already reports worktree git state; the
orchestrator should read it before restarting).
**Size**: M.

### Agent worktrees branch from whatever the project root's checkout happens to be

**Symptom**: `first-floor-worker`'s worktree HEAD is 6213025 (the old
integration branch the owner's checkout was on at 17:58), not `main`; a PR
"against main" from it would carry the whole squashed history.
**Evidence**: `git -C ~/.dark-factory/projects/factory/worktrees/first-floor-worker log -1`.
**Suggested fix**: base new agent branches on the project's default branch
(`origin/main`, or a per-project setting), never on the operator's current
checkout.
**Size**: S.
